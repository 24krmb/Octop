# 繁微 Fiona 期货市场预期数据

## 前置条件与 API Key

本 Skill 依赖 `rating_prediction`、`futures_market_data`、`futures_ranking` 和 `viewpoint` 四个 MCP。首次调用前检查当前工具列表；缺少某个工具时，先按 `templates/` 中对应平台的配置只添加缺少的 MCP。

- `rating_prediction` **需要 API Key**。实际鉴权使用 Bearer Token，在客户端凭证管理区将 API Key 配置为 `Authorization: Bearer <API Key>`。
- `futures_market_data`、`futures_ranking` 和 `viewpoint` 当前公开免鉴权，**不需要 API Key**，不要为它们配置 `Authorization` 请求头。

API Key 申请：目前暂不支持在线自助申请，请联系繁微对口销售或项目联系人获取。

不要把真实 API Key 粘贴到对话、Skill 文件或版本库中。`401`/`403` 时先检查 `rating_prediction` 的 API Key 与权限；连接超时或 transport error 时检查对应 MCP URL 和网络。

围绕“市场可能如何演变、当前共识是什么、依据是否充分、什么条件会使判断失效”组织分析。先建立可追溯事实，再整合市场预期、DZ 观点和统计比较，最后形成条件化情景。

## 能力定位

覆盖四类客户问题：

1. **市场预期与预期变化**：以 `rating_prediction` 的市场预期截面、daily/weekly 时间序列为主。
2. **行情与预期背离**：以市场预期数据为核心，使用行情、成交持仓、仓单和品种排名进行验证。
3. **DZ 观点辅助验证**：仅在客户明确询问 DZ 观点，或需要对市场预期进行辅助交叉验证时使用 `viewpoint`。
4. **条件化情景研判**：基于市场预期主数据形成基准、偏强、偏弱情景，并列出触发条件、验证指标和失效条件。

本 skill 使用四个 MCP：`rating_prediction` 是主要 MCP，`futures_market_data` 和 `futures_ranking` 用于事实与统计验证，`viewpoint` 仅作为辅助 MCP。`viewpoint` 只覆盖观点库、周度观点、研究员观点和动态快评，不等同于独立的 `report` 研报搜索/详情服务。

不把 `news`、`price_structure`、`report` 或 `dzlabel` 作为本 skill 的必需依赖。客户明确要求这些未接入的数据类型时，说明当前能力边界，不假设相关 MCP 已连接。

## 工作流程

按以下顺序执行。`rating_prediction` 是本 skill 的默认第一调用入口；只有代码转换、日期确认或需要事实验证时，才追加其他 MCP。不要因客户说“综合研判”就一次调用全部工具。

### 第一步：确认任务场景

- **当前市场共识**：必须调用 `rating_prediction` 截面工具；品种名称无法转换为代码时，才先调用 `futures_market_data`。
- **市场预期变化**：必须调用 `rating_prediction` 时间序列工具，不额外调用 `viewpoint`。
- **东证自有观点评分/方向**：调用 `rating_prediction` 的东证观点截面或时间序列工具，不调用 `viewpoint`。
- **观点库/周度观点/动态快评**：客户明确提出这些内容时，才调用 `viewpoint`，不把结果描述为市场整体预期。
- **行情与预期背离**：先调用 `rating_prediction`，再按需要调用 `futures_market_data`；需要横截面比较时才追加 `futures_ranking`。
- **多品种预期比较**：先调用 `rating_prediction`；只有客户同时要求价格或相对强弱时才追加行情或排名工具。
- **市场预期与观点库观点分歧**：先调用 `rating_prediction` 获取主数据，只有客户明确要求观点库对照时才追加 `viewpoint`。
- **综合情景研判**：按“市场预期主数据 → 必要的行情/排名验证 → 必要时补充观点库观点 → 情景输出”的顺序调用。

### 第二步：按需补充品种和事实基线

1. 客户已提供有效品种代码且问题只询问市场预期时，直接进入 `rating_prediction`，不先调用行情 MCP。
2. 客户只提供中文名称、别名或模糊代码时，调用 `futures_market_data` 的 `get_futures_product_info` 做代码转换；不得把合约代码直接当作 `product_code_list`。
3. 需要“最新”“今天”或“上一交易日”的行情验证时，才调用 `get_latest_futures_trading_date`，并记录实际有效日期。
4. 需要行情快照时调用 `get_futures_snapshot_quotes`；需要历史或主力变化时调用 `get_futures_timeseries_quotes` 或 `get_futures_dominant_quotes`。
5. 需要持仓、波动率或仓单作为验证证据时，按问题调用对应的 `futures_market_data` 工具；不为了丰富报告而全部调用。
6. 如果品种代码、报告类型或日期区间无法确认，先解决歧义，不进入预期分布和情景判断。

### 第三步：获取市场预期和 DZ 观点

#### A. 当前市场共识

1. 查询指定报告日的市场预期分布时调用 `get_market_expectation_cross_section`。
2. 客户未提供报告日时使用最新可用口径，但必须记录接口实际返回的 `data_date`。
3. 记录 `report_type`、样本数量、多空/中性分布、返回数量和是否截断。
4. 只能将结果描述为报告期观点分布，不得称为价格上涨概率或收益率预测。

#### B. 市场预期变化

1. 查询 daily 或 weekly 变化时调用 `get_market_expectation_timeseries`。
2. 明确 `report_type`、开始日期、结束日期和品种列表；daily 与 weekly 分开查询、分开解释。
3. 检查日期是否连续、是否存在报告缺口和是否被截断；缺失日期不补值。
4. 只有在时间区间、报告类型和品种对象一致时，才比较预期变化趋势。

#### C. DZ 观点

1. 客户询问东证自有观点的方向评分、观点截面或观点时间序列时，调用 `rating_prediction` 的 `get_dongzheng_viewpoint_cross_section` 或 `get_dongzheng_viewpoint_timeseries`。
2. 只有客户明确询问 DZ 观点库、周度观点或动态快评时，才使用辅助 `viewpoint` 的观点搜索、周度观点、动态目录、动态搜索和动态详情工具。
3. 输出时必须分开标注：`rating_prediction` 的东证自有观点，以及 `viewpoint` 的观点库/动态观点；两者不能合并为同一个“机构共识”。
4. 每条观点保留观点对象、研究员、发布时间、观点标识和原始文本摘要。
5. 不把动态快评当作完整研报，不把观点文本直接改写成事实。
6. 同一品种有多条观点时，先按时间和观点对象去重，再比较方向和证据范围。

### 第四步：统计和背离验证

1. 需要品种相对表现、板块统计或主力横截面变化时，先调用 `get_ranking_indicators` 确认指标；客户已明确指标时可跳过。
2. 按指标排名调用 `get_product_ranking`；查询板块区间统计调用 `get_section_statistics`；查询主力横截面变化调用 `get_dominant_cross_section_change`；查询单品种概览调用 `get_symbol_overview`。
3. 将行情、成交持仓、仓单、排名和预期分布放在相同或可解释的实际日期上比较，不把不同日期强行拼接。
4. 检查 `total`、`returned`、`truncated` 和 `hint`；截面不完整时只能描述返回样本，不得推导完整市场排名。
5. 背离只能先写成观察事实，再给出可能解释；没有事件数据时，不编造新闻原因或供需原因。

### 第五步：组合处理和停止条件

- 只问当前共识：`rating_prediction` 截面 → 输出分布和限制。
- 只问预期变化：`rating_prediction` 时间序列 → 输出趋势和缺口。
- 只问东证自有观点：`rating_prediction` 东证观点截面/时间序列 → 输出东证观点来源和差异。
- 只问观点库/动态观点：标准化品种/日期 → `viewpoint` → 输出观点来源和差异，不描述为市场整体预期。
- 问观点分歧：`rating_prediction` 主数据 → 只有客户明确要求观点库对照时才追加 `viewpoint` → 按日期、对象和证据范围对齐。
- 问行情与预期背离：`rating_prediction` → 按需要追加 `futures_market_data` → 需要横截面比较时再追加 `futures_ranking`，不默认调用 `viewpoint`。
- 问综合情景：`rating_prediction` 市场预期 → 必要的行情/排名验证 → 按需补充 `viewpoint` → 基准/偏强/偏弱情景。
- 当关键证据缺失、接口为空、结果截断或客户问题已经得到回答时停止，不用其他 MCP 猜测缺口。

### 第六步：形成情景并输出

1. 将材料分成事实、市场结构、市场预期分布、东证自有观点、观点库观点、推断、反向证据和不确定性。
2. 每个情景写明触发条件、观察窗口、验证指标、反向因素和失效条件。
3. 证据不足时只输出情景排序和待验证事项，不给概率、目标价、买卖点或买卖建议。
4. 输出前逐项核对品种/合约、实际日期、报告类型、观察区间、MCP 工具、样本数量和截断状态。

## 数据与情景组织规则

### 市场预期

- 机构观点分布表示报告期观点的统计分布，不是价格上涨概率、收益率预测或交易信号。
- `daily` 与 `weekly` 是不同报告口径，不能直接拼接成连续时间序列。
- 必须区分报告日期、实际数据日期、查询日期和自然日期；以接口实际返回日期为准。
- 样本量不足或结果被截断时，只能描述“返回样本中的分布”，不能描述完整市场共识。

### DZ 观点

- 观点库结果不是客观事实，必须标记观点来源、研究员、发布时间和观点对象。
- 不同研究员的观点不能只按“看多/看空”计数，还要比较时间、对象和证据范围。
- `viewpoint` 的动态快评不能当作完整研报；需要研报正文时应明确能力缺口。

### 行情、统计与归因

- 同时发生不等于因果成立；异动解释需对齐行情时间、统计日期、观点发布时间和数据实际日期。
- 行情、排名、市场预期和观点冲突时并列呈现冲突，说明各自覆盖范围和证据强度。
- 用“已确认 / 较高可能 / 可能相关 / 证据不足”表达证据强度，不使用绝对化措辞。
- 不把单一排名、仓单、持仓或观点直接扩写为未来涨跌结论。

## 工具协同与降级

- 不调用 SDK、`finosdk-query` 或自行构造 HTTP 请求替代已注册 MCP。
- `futures_market_data` 负责事实基线，不负责市场预期结论；`futures_ranking` 负责统计比较，不等于供需基本面分析。
- MCP 不可用、无权限、返回空结果或覆盖不足时，说明缺失的证据类型，并缩小研判范围。
- 没有足够证据时输出情景排序和待验证事项，不补造新闻、基本面、观点、概率或价格目标。

## 输出结构

按问题裁剪，通常采用：

1. **结论摘要**：基准情景、判断强度和最重要依据。
2. **数据时点与口径**：品种/合约、实际截止日期、观察区间、报告类型、MCP 工具和覆盖范围。
3. **当前证据**：基础事实、统计排名、市场预期分布和 DZ 观点。
4. **传导链条**：驱动因素、作用对象、时间尺度和反向因素。
5. **情景分析**：基准/偏强/偏弱、触发条件、验证指标和失效条件。
6. **风险与缺口**：滞后、截断、样本不足、观点冲突和待核实事项。

## 示例问题

- 结合市场预期分布、DZ 观点和近期统计，研判某品种未来两周的基准、偏强和偏弱情景。
- 某品种价格异动时，区分基础事实、预期变化和可能的传导路径，并列出后续验证指标。
- 比较多个品种的市场预期、观点分歧和相对强弱，说明哪些结论受到样本截断影响。
- 当前市场预期与 DZ 观点不一致时，梳理分歧来源、证据强弱和可能的失效条件。
